# 006 Kria boards: KV260 and KR260

Status: partial. The `k26` device model, the `kv260` and `kr260` Vivado
projects, the register shell and the register map are built and tested against
a Vivado stub. Nothing has been through real Vivado or run on a board yet,
`deploy(host=...)` waits for a Kria runtime, so `load_weights`
([003](003-reloadable-weights.md)) runs only against the register file under
Verilator, and the example MLP fits the K26 only with one layer on multipliers
(see Resources).

## Why these boards

Both carry the same K26 module, with the UltraScale+ fabric trading firms use in
their Alveo cards: DSP48E2 slices, UltraRAM, GTH transceivers. Closing timing on
it at 322 MHz means something to anyone who builds trading hardware, and Vivado
is free for the part.

They differ in one way that matters to us. The KV260 carrier has no SFP+ cage:
AMD's board file wires only the SOM connector that lacks the GTH transceivers.
The KR260 carrier has one SFP+ cage, on GTH quad 224 lane 2 with a 156.25 MHz
reference clock. So the KV260 can run everything except the 10G network, and
the KR260 can run all of it. The device model is the same for both.

## Behaviour

`k26` is the XCK26 on the SOM, part `xck26-sfvc784-2LV-c`. Its budget comes
from AMD's K26 SOM data sheet (DS987 v1.2, Table 5): 117120 LUTs, 234240 flip
flops, 1248 DSP48E2 slices, 144 block RAMs of 36 kbit and 64 UltraRAMs. The
same data sheet gives the speed grade as -2LV, a -2 die run at VCCINT = 0.72 V.
DSP packing follows the vu9p rules: two int8 or four int4 products per DSP48E2.
The clock is 322.265625 MHz, the 10GBASE-R rate on a 32 bit datapath. That is
the target we constrain to, not a measured fmax.

`build(board="kv260")` or `build(board="kr260")` takes a fixed latency design
compiled for `k26` and writes a Vivado project into `<out_dir>/<board>/`:

| File | What it is |
|---|---|
| `kria_shell.v` | The Hardcaml generator's `kria` output: an MMCM, a reset synchroniser, the AXI4-Lite registers and the accelerator. |
| `kria_top.v` | The Vivado top, which wires the block design to `kria_shell`. |
| `build.tcl` | Creates the project and the block design, then runs synthesis, implementation, the timing report and the bitstream. |
| `settings.tcl` | The board name, part, base address and job count `build.tcl` reads. |
| `kria.xdc` | The 322.265625 MHz clock on the MMCM output, `-period 3.103`. |
| `sfp.xdc` | KR260 only. The SFP+ pins and the 156.25 MHz reference clock, added to the project disabled. |

If `vivado` is on PATH, `build` then runs `vivado -mode batch -source build.tcl`
in that directory. That leaves `<board>.bit`, `<board>.bin` for the Linux FPGA
manager, `<board>.xsa`, `timing_summary.rpt` and `utilization.rpt` beside the
sources. Without Vivado, `build` writes the project anyway and raises
`ToolchainError` in one sentence that says where it is.

The block design holds the Zynq PS, with `M_AXI_HPM0_FPD` set to 32 bits, and
an AXI SmartConnect that turns it into AXI4-Lite. Its `pl_clk0` runs at 100 MHz,
and the shell's MMCM multiplies it by 103.125 and divides by 8 and then 4, which
gives 322.265625 MHz exactly from a 1289.0625 MHz VCO. The same clock drives the
PS's AXI port, so the whole design is one clock domain. The shell's window is
64 KiB at 0xA0000000.

On the KR260, `sfp.xdc` places `sfp_rx_p/n` on T2 and T1, `sfp_tx_p/n` on R4
and R3 (`GTHE4_CHANNEL_X1Y12`), and the reference clock on Y6 and Y5
(MGTREFCLK0_224), as taxi's KR260 example does. It is disabled until the MAC
of [007](007-tick-to-trade.md) stage B arrives, with taxi as an external
dependency.

The ARM cores run Linux. They host the weight reload path from
[003](003-reloadable-weights.md) over AXI4-Lite and a small runtime for
`predict` while testing. In the trading demo the data path never touches the
ARM: features come from the network and decisions go back out.

## Register map

`build` writes this map into `manifest.json` under `registers`, with the base,
the span and each register's offset, access and size, so software other than
ours can drive the board. Offsets are bytes from 0xA0000000, and every
register is 32 bits.

| Offset | Name | Access | Meaning |
|---|---|---|---|
| 0x0000 | `id` | r | 0x4F544631, "OTF1" |
| 0x0004 | `latency` | r | The design's latency in cycles. |
| 0x0008 | `feature_bits` | r | Width of the features bus. |
| 0x000C | `prediction_bits` | r | Width of the prediction bus. |
| 0x0010 | `control` | w | Writing 1 raises `features_valid` for one cycle. |
| 0x0014 | `status` | r | Bit 0 is set when the prediction arrives, cleared by the next start. |
| 0x0018 | `cycles` | r | Cycles from the last start to its prediction. |
| 0x0020 to 0x0034 | `weights_*` | | The reload control of [003](003-reloadable-weights.md). |
| 0x1000 | `features` | rw | The features, element 0 in the low bits of the first word. |
| 0x2000 | `prediction` | r | The last prediction, laid out the same way. |
| 0x8000 | `weights` | w | The idle weight bank of 003; reads 0, and writes are ignored when the weights are frozen. |

`cycles` reads back what the hardware counted, so a board run checks the
latency as well as the answers. The shell takes one transfer at a time each
way, always answers OKAY, and ignores write strobes.

`runtime/host/kria_run.cpp` is the runtime sketch for the ARM. It maps the
window through `/dev/mem`, checks `id`, writes `golden/input.hex` into
`features`, starts, polls `status`, compares `prediction` with
`golden/expected.hex` and prints `cycles`.

## API

```python
acc.compile(device="k26", mode="fixed")
acc.build(board="kr260")
acc.summary()                      # measured fmax beside the estimate, once Vivado has run
acc.deploy(host="kria.local")      # NotImplementedError until the Kria runtime
acc.load_weights("new.onnx", registers=regs)   # spec 003
```

The shell's MMCM and constraints run the design at 322.265625 MHz.
`clock_mhz=322.265625` ([002](002-pipelined-matvec.md)) pipelines the model
for that clock; without it the model keeps three stages a layer and may not
close there. `build` on a Kria board without a compiled
design compiles for `k26` in fixed mode first. A streaming design raises
`ConfigError`, since the shell feeds one vector per start.

When a `timing_summary.rpt` is in a board directory under the build, `summary()`
adds a line such as

```
 Clock: 322.3 MHz estimated, 337.2 MHz measured by Vivado (WNS 0.137 ns, kr260/timing_summary.rpt)
```

where the measured figure is `1000 / (period - WNS)` for `otf_clk`. Those
numbers come from the canned report in the tests, not from a real run.

`onnx2fpga synth --device k26` synthesises each streaming unit out of context
on the K26 part, as it does for vu9p, and `--period` now defaults to the
device's clock, 3.103 ns here.

## Resources

The example MLP, 32-64-16-10, does not fit on multipliers alone. Unrolled it
needs 1706 DSPs on the compiler's estimate, which already assumes two int8
products per slice, and the K26 has 1248, of which the default 80 percent
utilisation allows 998. yosys packs no products together and maps 2853.

Constant arithmetic ([004](004-weight-specialised-arithmetic.md)) trades those
DSPs for LUTs, and by default every layer takes it. Then the MLP needs 102618
LUTs and 90 DSPs, past the 93696 LUTs the 80 percent limit allows. Each layer
picks the arithmetic that keeps its own busiest resource lowest, so the choice
never sees the sum. With fc1 on multipliers the MLP fits:

```python
acc.layers["fc1"].arithmetic("multiplier")
acc.compile(device="k26", mode="fixed")
```

| Layer | Arithmetic | LUT | DSP |
|---|---|---|---|
| fc0, 32 to 64 | constant | 59364 | 64 |
| fc1, 64 to 16 | multiplier | 21504 | 528 |
| fc2, 16 to 10 | constant | 6064 | 10 |
| Total | | 86932 (74.2%) | 602 (48.2%) |

The latency stays 9 cycles, 27.9 ns at 322.265625 MHz. `utilisation=1.0`
instead keeps constant arithmetic everywhere at 87.6 percent of the LUTs. Both
are the compiler's estimates; Vivado has not placed either. The tests build a
16-32-8 MLP, which takes constant arithmetic in both layers for 26000 LUTs and
40 DSPs, because it builds faster.

## Verification

Without Vivado, `tests/test_kria_board.py` runs the generated `build.tcl` through
`tests/fake_vivado`, the same tclsh stub `synth` is tested with. The stub fails
on any command it does not know and on any file `add_files` names that is not
there, and it sources the XDC files so their syntax is checked too. The test
checks the part number, the files, the 3.103 ns clock, the base address, the
disabled `sfp.xdc` on the KR260 and its absence on the KV260, and the runs up to
the bitstream. Verilator lints `kria_top.v` against `kria_shell.v` and
port-accurate stand-ins for the block design wrapper, `MMCME4_BASE` and `BUFG`.
The timing parser reads a canned report in Vivado's layout. `kria_run` runs
against a sparse file standing in for `/dev/mem`.

The Hardcaml test `test_kria_regs.ml` drives the register shell over AXI4-Lite
from a random initial state. It writes features, starts and polls 20 times, and
every prediction matches the software model of the two layer test design.
`cycles` reads 6 each time, the design's latency, and the reserved window
reads 0 after a write.

## Open questions

- PYNQ on the Kria, or plain Linux and our own small C++ runtime from
  `runtime/`? We started on the second with `kria_run`.
- The bitstream reaches Linux as `<board>.bin` from `write_bitstream -bin_file`.
  Loading it with `fpgautil` or `xmutil` also needs a device tree overlay, and
  we have not written one.
- Should the KR260 take its clock from the 156.25 MHz SFP+ reference instead of
  `pl_clk0`? That would make the fabric clock exactly the MAC's in stage B, if
  U90 runs without being programmed first.
